# 后端竞争力路线图

> 基于对 Open WebUI / LibreChat / AnythingLLM / LobeChat / Cherry Studio 的源码与 issue 调研
> （2026-10-18，本地副本在 `C:/Users/FLYF/Downloads/flyweb/_refs/`）。
> 只讨论**后端/协议/数据层**，不涉及视觉与交互。

## 0. 本轮进展（2026-10-18 已交付）

调研时发现的 P0，已经做完一半：

- ✅ **工具调用 / 服务端 agent 循环**：内置 `web_search` / `fetch_url` / `current_time`
- ✅ **知识库 RAG**：零原生依赖，SQLite BLOB 向量 + 中文混合检索
- ✅ **OpenAI 兼容网关 `/v1`**：任何支持自定义 OpenAI 接口的客户端都能接
- ✅ **模型降级链 `FALLBACK_MODELS`**：重试耗尽后自动换备用模型
- ✅ **消息树 `parent_id`**：分叉 / 编辑重生成 / variants 轮播 / 上下文只取激活分支
- ✅ **成本硬上限**：请求前预检，超限 429，80% 软提示
- ✅ **摘要式上下文压缩**：丢历史前先用小模型总结，带缓存，可一键关闭
- ✅ **上游错误归一化**：`auth_failed / quota_exceeded / rate_limited / model_not_found / context_overflow / content_filtered / server_error / timeout`
- ✅ **全量导出 / 导入**
- ✅ **MCP 客户端**：自研 JSON-RPC 子集（未引官方 SDK），stdio + Streamable HTTP，带信任模型与单工具禁用
- ✅ **上传链路异步化**：上传立即 202，后台流水线带进度/阶段/重试，并发受控，进程重启不丢任务
- ✅ **预设（Preset）**：模型 + 参数 + 系统提示 + 知识库 + MCP 组合打包成可复用条目；
  `/v1` 里以 `preset:<id>` 暴露，第三方客户端可直接选用
- ✅ **`/v1` 错误形状改成 OpenAI 标准**（`{error:{message,type,code}}`），SDK 才能读到错误文案
- ✅ **多用户 + 角色**：`MULTI_USER=true` 开启，scrypt + HttpOnly 会话，admin/user 两档，
  会话按用户隔离（越权读返回 404 而不是 403）
- ✅ **文档解析扩展 + 网页入库**：PPTX / XLSX / HTML 去标签；`url` 直接入库
  （SSRF 逐跳校验），对应 Open WebUI 最高赞 issue #5872「知识库接不了外部数据源」的低成本版本
- ✅ **会话文件夹与标签**：删除文件夹不删会话；标签入口清洗 + 精确过滤（「重要」不会匹配「不重要」）
- ✅ **小任务接口**：`/api/tasks/:kind`（title / summary / suggest / rewrite），
  统一走子任务模型 + 预算 + 记账
- ✅ **检索增强**：四路信号（余弦/关键词/硬词/章节）+ MMR 去重；按文档限定检索；
  `debug:true` 返回每条候选的分数明细与耗时（对应 AnythingLLM #4338 / #1505 的抱怨）
- ✅ **分享页社交预览**：`/s/:id` 注入 OG / Twitter meta，微信/Slack/飞书能出预览卡片；
  密码分享不泄露内容、标题做 HTML 转义
- ✅ **个人访问令牌（PAT）**：补上「多用户模式把网关关掉」的洞，第三方客户端可用
  `Authorization: Bearer fcp_...` 接入 `/v1`
- ✅ **图像生成**：`/api/images/generations` + `/v1/images/generations`；
  注册 `generate_image` 工具（`imageGeneration` 开关 / 预设可绑定），
  图片走 SSE 而不进模型上下文

## 0.1 一句话结论

我们已经在「协议层」追平了主流自托管产品的底座（多服务商、流式、上下文预算、持久化、
工具调用、知识库、OpenAI 兼容网关）。**真正的差距不在模型接入，而在三件事**：

1. **会话的数据结构**：他们用「消息树（parent_id）」，我们用「线性数组」——这决定了能否分叉、
   编辑后重生成、对比不同分支，是体验分水岭。
2. **多用户与配额**：他们要么做了完整 RBAC，要么完全没做。**没有人做好「成本硬上限」**，这是空档。
3. **上下文管理**：他们开始用「摘要压缩」而不是「丢弃最早消息」，长对话体验差距明显。

## 3. 用户最痛的诉求（来自真实 issue）

> 这些是调研时抓到的、按 👍 排序的高频抱怨，直接决定口碑。

1. **「对话太长就失忆 / 报 context length 错误」**——我们已有裁剪，但需要摘要化（P0-3）。
2. **「想改一句话重答，只能新建会话」**——消息树缺失（P0-1）。
3. **「一个 Key 被全公司用，月底账单吓人」**——配额缺失（P0-2），三家都没解决。
4. **「上传的 PDF 里明明有答案，就是搜不到」**——检索质量问题。我们的混合检索 + 中文 2 字窗
   在这点上比三家默认配置更稳。
5. **「部署太重，装个聊天界面要拉 Python + 向量库」**——我们的单进程 + 零原生依赖是明确优势。
6. **「想用自己的客户端接这个服务」**——OpenAI 兼容网关（本轮已补）。

## 4. 我们的差异化打法

不做「功能更多的 Open WebUI」，做**「部署最轻、成本最可控、中文最好用」的那一个**：

- **零原生依赖**：Node 内置 SQLite + JS 向量扫描，`npm install` 完就能跑，Docker 镜像小一个数量级。
- **成本可见可控**：每个请求都有 token 与估算花费，下一步加硬上限——这是三家共同的空档。
- **中文优先**：切块按中文标点与标题层级，检索用中文 2 字滑窗，而不是把英文方案硬套过来。
- **可被集成**：`/v1` 兼容网关让 FlyChat 能当任何客户端的后端。

## 5. 明确不做

- **不做向量数据库全家桶**（Milvus/Qdrant/Weaviate 适配）。个人规模用不上，维护成本极高。
- **不做双进程架构**（collector + server 分离）。AnythingLLM 这么做是为了支持海量文档，
  代价是部署复杂度翻倍。
- **不做模型微调/训练**。与「聊天产品」定位无关。
- **不抄 Open WebUI 的「函数（Functions/Pipelines）」体系**。它是 Python 生态的产物，
  我们用 MCP + 内置工具覆盖同样场景，且不需要用户写 Python。
